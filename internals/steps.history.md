History, not rules: AGENTS.md's Steps win where they differ.

- `apparmor` is never mirrored in devopsy-cli's end-to-end servers: on a host with AppArmor (GitHub's Ubuntu runners included) it would start confining the inner containers, changing what the suite tests. The socket buffers neither: a container cannot set `net.core`.
- LLMNR: Debian 13's resolved answered on port 5355 of every address, the one host service but SSH listening publicly (found on a DigitalOcean server, 2026-10-29). Ubuntu 26.04's has LLMNR off already (`resolvectl status`: `-LLMNR`); set on both, should a default change. OrbStack masks resolved.
- kexec's memory: Ubuntu 26.04's kernel (7.0) turns Kexec HandOver on and marks its scratch memory CMA, for movable pages only, so page tables, slab and socket buffers share the rest: 646 MB of 2 GB on DigitalOcean, 1.25 GB on Vultr, where its image also reserves 320 MB for kdump (checked 2026-10-29; DigitalOcean's has no kdump). kdump a setting and KHO not, and `kho=off` on every server rather than only where a kernel has `CONFIG_KEXEC_HANDOVER_ENABLE_DEFAULT=y`, were decided with the maintainer (2026-10-29): a Debian release upgrade brings such a kernel, and Debian 13's 6.12, without KHO, passes the word to user space ("Unknown kernel command line parameters"), checked on Vultr. Vultr's `ubuntu-server-minimal` depends on kdump-tools, hence disabled, never purged. Checked on Vultr's Ubuntu: no CMA block and 320 MB more after the reboot, the system `running`.
- unattended-upgrades takes the restart flag even on a day with nothing to upgrade: its 2.12's `reboot_if_requested_and_needed`, after every run that writes its stamp.
- The socket buffers: `cloudflared` (quic-go) asks for 7.5 MB. Compose's `sysctls:` are the container's namespace, and `net.core` is not among them, so neither the Traefik nor the tunnel template could set it. Before, both the buffers and `vm.swappiness` were applied only when written, so a first run failing at `sysctl` left the file and every rerun skipped it.
- `daemon.json` merged: written whole, a rerun dropped a proxy's `proxies` (found on a server behind an HTTP proxy, 2026-10-27), and Docker then pulled nothing. Decided with the maintainer over a prompt with a diff, as dpkg asks for a conffile: setup.sh runs every step on every run, often without a terminal (`curl | bash`), with nowhere to remember a "keep mine". Compared as JSON so the heredoc of before was not rewritten. A key no longer set is left (lean checks).
- Docker's AppArmor detection is containerd's `HostSupports`, behind a `sync.Once` (securityfs, the kernel's `enabled` flag, `/sbin/apparmor_parser`). Not testable on OrbStack, whose kernel has no AppArmor: there the step only says so.
- Block volumes: DigitalOcean mounts an attached volume on `/mnt/<volume>` with its own systemd mount unit. `setup.sh` does not mount them.
- Other users' processes: a review of devopsy-cli's session variables (2026-11-11) found that every session's script, the operator's command in it, is one argument of `ssh` and of the server's `sh`, so every user reads it in `ps` while it runs, a project user included. `hidepid=invisible` with an exempt group was taken over anything per user (the kernel has no such option) and over a setting: setup.sh knows nothing of project users, who come later, and a server without them loses only a non-root admin's full `ps`. Tested on OrbStack machines (Debian 13, Ubuntu 26.04, kernel 7.2): a ssh login, its logind session and the user's systemd manager all work without exempting logind, which uses pidfds; polkit fails ("Failed to open file /proc/<pid>/status") until in the group; the mount refuses a group's name (`proc: Bad value for 'gid'`); the fstab line holds across a restart, and with `defaults` it dropped `/proc`'s `nosuid,nodev,noexec`. devopsy-cli reads only its own user's processes, root's, or the host's through a container's fresh `/proc` (`--end-uid` under `--pid host`).
- The swap step skipped everything once any swap was on, so a run cut between `swapon` and the fstab line never wrote the line, and the swap was gone after a reboot. Each of the three is now checked apart.
- The docker step's `daemon.json` merge (with its `DEVOPSY_ADDRESS_POOLS` setting) and the socket buffers went to devopsy-cli's `--server-setup`, and `step_user_root` stopped making and giving the release root's directory, which `--server-setup` does (making it when missing, giving it only when root owns it and it is empty). A first run of setup.sh now starts Docker once (its install), twice where the AppArmor restart applies, against systemd's three starts a minute; `--server-setup` clears the start counter before its own restart. The e2e servers' `daemon.json` became devopsy-cli's own.
- The kexec drop-in was one file of setup.sh's, `zz-devopsy.cfg`, until devopsy-cli's how-to topics (`kexec-handover`, `kdump`) wrote `zz-kho-off.cfg` and `zz-no-crashkernel.cfg` (2026-11-13): setup.sh now writes those two with the topics' text, so a server set up either way is the same, and a server set up before keeps `zz-devopsy.cfg` until it is removed by hand. The removal of another list of Docker's repository came from the `docker` topic too.
