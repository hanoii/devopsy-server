History, not rules: AGENTS.md's Rules win where they differ.

- Ubuntu's coreutils: Ubuntu ships Rust's uutils beside GNU's and may make them the default. 26.04 on DigitalOcean had GNU's (checked 2026-10-26); OrbStack's 26.04 and a server upgraded from 24.04 have `coreutils-from-uutils` marked manual (checked 2026-10-27), where a plain install of GNU's failed, apt keeping the manual one.
- A setup script, not a CLI: step names, subcommands and an installed copy that updated itself all existed and were removed, with the `ci-key` step.
- Never rebooting, and the flag only when a reboot changes something (the maintainer, 2026-10-29): a flag for nothing, as on Debian 13's 6.12 for KHO, would be a banner asking for a reboot that changes nothing, and an automatic one taking the sites down for it.
- Docker's `daemon.json`, the socket buffers, the release root's directory and the block volume's `RequiresMountsFor` drop-in moved to devopsy-cli's `--server-setup`, which keeps them as devopsy wants them on every server, asks before replacing what someone else set (setup.sh could not ask under `curl | bash`) and records the answer, and adds the metadata firewall. setup.sh names the command last instead of running it: it runs on the operator's machine, as the deploy user, and asks. Nothing setup.sh wrote before is removed or migrated: devopsy adopts the same four values, and puts its own header on the sysctl file at its first run.
- The deploy user's devopsy config was setup.sh's whole while its first line was the marker: a rerun rewrote it as the marker and `releases: root`, or deleted it without `DEVOPSY_ROOT`, dropping what devopsy appends to the same file (its `door:`, without which every project user on the server stops working). Now the step owns only its three lines at the top. Without a root, the rest stays unmarked, a file setup.sh no longer touches: a later `DEVOPSY_ROOT` warns, as for any file it did not start, rather than putting its block back above lines that are someone else's.
- Other users' processes hidden moved to devopsy-cli's `--project-users setup` (2026-11-13), with its own `devopsy-proc.service` in place of the fstab line, only on a server with project users, a choice there: without project users the deploy user, root through Docker, is the one who reads `ps`. A server setup.sh set up before keeps its fstab line, group and polkit drop-in, which devopsy judges by `/proc`'s mount (hiding, `gid=` a group the deploy user is in) and reads in sync. `polkitd` left `test/Dockerfile` with the checks.
- `DEVOPSY_SUDO` and `DEVOPSY_APT_PACKAGES` were dropped (2026-11-13, with the maintainer): extra packages are the admin's `apt install`, not host setup, and passwordless sudo gave a root-equivalent user root in one word. The base packages shrank to what devopsy and the steps use: `git`, `jq`, `openssl` and `sudo` ran nowhere on a server (`jq` was only `test/run.sh`'s, now in its image), and `sudo` is installed for project users by devopsy-cli's how-to. A server set up with `DEVOPSY_SUDO=1` keeps its sudoers file until removed by hand.
- The release root left setup.sh (2026-11-13, with the maintainer): devopsy-cli's `--server-setup`, which already made the directory and Docker's wait for its mount, and lists the volumes it could be on, asks for it and writes `releases: root` itself. Gone with it: `DEVOPSY_ROOT`, the three-line block at the top of the deploy user's devopsy config and the test of the lines after it. A server set up with `DEVOPSY_ROOT` keeps its block, which devopsy reads as any `releases: root`, its marker a comment.
- The questions (2026-11-13, with the maintainer): settings were environment variables only, saved and reused, so a change needed knowing the variable's name. Every run at a terminal now asks each one again with its current value, the update being where a setting changes; the environment stays for scripted runs and is never asked, and `--yes` asks nothing at a terminal. `/dev/tty` is what makes `curl | bash` over SSH ask: its stdin is the script. An empty variable once meant its default; now `none` and `never` are words and saved empty. The swap size became the memory's by default, the swap a setting that applies both ways (resized, removed), where before a size applied only to a server with no swap.
- Every step but the base packages got a question of its own (2026-11-13, with the maintainer): the deploy user and the swap had one already, unattended upgrades got `DEVOPSY_SERVER_UPGRADES`, a yes or no question defaulting to yes. Docker and devopsy are what make the server a devopsy server, so instead of a question each, a run at a terminal first asks whether to go on, covering the base packages, Docker and devopsy together, `n` stopping it. The distribution's question moved onto the same yes or no helper, so a wrong answer there is asked again rather than taken for no.
- The output was made devopsy's (2026-11-13, with the maintainer): `[devopsy-server]` in cyan on every line, whatever its level, became `devopsy-server: ` with devopsy's tags, the step's name taken from the function saying it, reasons moved to `| ` detail lines and the next command after `$ `, colored only at a terminal (cloud-init's log had the escapes in it). The questions took devopsy's `[Y/n]`, the opening one split into what it installs and `continue?`, and the user step says it copied root's keys only when it adds one. LLMNR and multicast DNS became a question and a setting, `DEVOPSY_SERVER_LLMNR`, a step of their own, and kexec's memory a step too, so the base step is only the packages.
